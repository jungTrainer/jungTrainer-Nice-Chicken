# IMP-14 이후 보완·발전 계획

2026-10-13. 기준은 IMP-13 최종 `c7402dd`, 회귀 검사 197개다. 이 문서는 구현 전 계획이다. IMP-14는 기존 로드맵 범위를 따르고 IMP-15~19는 제안 번호이며, 앞 단계의 측정 결과에 따라 범위를 조정한다.

## 현재 판단과 방향

사용자 추가 방향: 백엔드·계정·서버 쿠폰 검증 작업은 제외한다. 음료 1병(테이블의 방문당 1회)·양배추·무 서비스와 오프라인 반복 플레이, 지역 엔딩/난이도, 온라인일 때의 점진적 광고를 중심으로 한다. 최신 실행 순서와 기획 제안은 [제품 방향 제안](product-direction.md)을 따른다. 아래 IMP-15~19 표는 추가 의견 이전의 구조/안정성 계획이며 새 방향 문서에서 우선순위를 재조정했다.

정산·저장 호환·직원/지점·미션·연구·엔딩·PWA·다중 창의 기본 규칙은 구현하고 Chromium에서 검사했다. 다음 목표는 장애에서 진행을 보존하고, 플레이어가 현재 운영/저장/복구 상태를 이해하며, 여러 기기에서 수일 운영을 안정적으로 이어가는 것이다. 그 기반 위에서 구조와 콘텐츠를 발전시킨다.

확인한 근거는 [IMP-13 보고서](improvements/IMP-13-session-ownership.md), [작성자 정책](session-ownership.md), [실행 계약](runtime-architecture.md), [성장 정책](economy-policy.md), [콘텐츠 설계](content-design.md)다. 다음 위험은 코드 점검으로 확인한 경로이며 이번 계획 작성에서 새 장애를 실행·재현한 결과는 아니다.

- `readSavePayload()`는 JSON parse 후 본 저장/backup을 선택한다. 파싱 성공과 게임 데이터로서의 유효성·지원 버전·최신성은 별개다.
- `save()`는 이전 본 저장 원문을 backup에 먼저 쓰고 새 본 저장을 쓴다. 본 저장이 손상되어 정상 backup에서 시작한 경우, 후속 저장이 정상 backup을 손상 원문으로 교체할 수 있다. 그때 본 write까지 실패하면 복구 원본을 잃을 위험이 있다.
- reset의 본 저장 성공과 backup 삭제는 별도 연산이다. 삭제 실패 후 오래된 진행이 복구 후보로 남는 경로를 확인해야 한다.
- Web Locks 미지원은 읽기 전용이며, 실제 Firefox/WebKit·모바일 OS의 잠금/숨김/설치는 Chromium 합성 검사와 구분해야 한다.
- 수일 목표는 연속 운영 모델 약 98.5시간이다. 오프라인 8시간 한도·고객 이동/이탈·실제 방문 주기가 있어 실제 달력 시간의 보장이 아니다.
- `main.js`는 4,339줄이며 화면·입력·장면·게임 루프의 책임이 남아 있다. 수동 점검표는 IMP-09의 92개 기준이다. 신규 기능을 늘리기 전에 변경 경계와 검증 안내를 정리할 필요가 있다.

## IMP-14 실행 계획

1. **현재 실패 경로를 재현한다.** 본/backup 각각의 손상·둘 다 손상·JSON만 유효한 잘못된 데이터·읽기 거절·backup write 실패·본 write 실패·reset 삭제 실패를 조합한다. 저장 원문, 현재 메모리, dirty, 작성자, 확정 미수령과 paid 이력을 비교한다.
2. **복구 판단을 쓰기와 분리한다.** 후보 검사/출처/지원 버전을 먼저 결정하고 원본을 보존한다. 검증과 명시적 복구 전에는 손상 데이터를 기본값이나 오래된 후보로 자동 교체하지 않는다. 안전하게 진행할 수 없으면 원본 백업과 읽기 전용 안내를 제공한다.
3. **호환 정책을 정한다.** 구 저장과 알려지지 않은 확장 필드를 유지하면서 검증·정규화·필수 migration을 구분한다. 필요하면 revision/초기화 세대 등 metadata를 검토하되, 이 값과 checksum은 서버 인증이나 조작 방지가 아니다. 오래된 저장의 최신성·지급 여부를 추측 생성하지 않는다.
4. **사용자가 복구 후보를 이해하게 한다.** 본 저장/backup/이 창 미저장본을 구분하고 후보의 시각·지점·보유금·확정 미수령·지원 여부를 보여 준다. 오래된 후보에서 최신 지급 이력을 증명할 수 없다면 그 한계를 설명하며 자동 합산·추가 지급하지 않는다. 복구 전 원본 내보내기, 명시적 선택, 취소와 재시도를 제공한다.
5. **다중 키 실패 정책을 결정한다.** 같은 키의 단일 쓰기와 여러 키 변경을 구분한다. 현 구조의 보존 정책으로 요구를 충족하는지 측정하고, 충족하지 못하는 부분에 한해 원자적 저장 구조나 IndexedDB transaction을 별도 설계한다. 전체 DB 이관을 미리 확정하지 않는다. 이관이 필요하면 구 저장 읽기·commit 확인·실패 rollback·구 창 대응을 먼저 정의한다.
6. **실제 브라우저로 확인한다.** Chromium의 다중 탭/설치 창·온라인/오프라인·재접속·인계·지점·import/reset을 유지한다. 가능한 Firefox/WebKit에서 저장/잠금/숨김 기능을 확인하고 지원·읽기 전용·미검증을 구분한다. WebKit 자동 검사를 실제 iPhone 설치 검증으로 취급하지 않는다.
7. **기록을 갱신한다.** 현재 197개를 보존하고 새 실패/복구 검사를 추가한다. 수동 점검표의 오래된 92개 기준과 PWA·다중 창 누락을 갱신한다. 로그·PNG·실패/재시도 원문 비교, 정책·완료 보고서·다음 프롬프트를 남긴다.

## IMP-15~18에서 보완할 내용

사용성은 화면 크기 대응에서 실제 과업 완료로 검증 범위를 확장한다. 이름 입력→첫 구매→연구/메뉴 선택→미션→지점 이동을 따라갈 수 있게 안내하고, 미수령/저장 완료/읽기 전용/업데이트 대기 상태를 구분한다. 안내 확인·이야기 읽기·창 닫기는 지급 동작으로 연결하지 않는다. 저장 실패와 인계 요청 알림이 키보드·스크린리더 포커스를 빼앗지 않는지 확인한다.

장기 검증은 첫 표본으로 30~60분 실제 브라우저 운영과 7~30일 가속 시나리오를 제안한다. 가속 검사와 실제 운영 시간은 별도 결과로 기록한다. 서비스 처리량·각 ledger·paid 이력·지점/캐시 소유권과 listener/rAF/타이머 수·메모리·DOM 갱신·저장 비용을 비교한다. 매 PR의 짧은 회귀와 긴 검사의 실행 주기를 구분하고, 기기 편차가 큰 실행 시간을 근거 없이 CI 실패 기준으로 삼지 않는다. 진단은 우선 로컬 합성 자료로 수행하며 실제 사용자 백업을 자동 업로드하지 않는다.

구조 개선은 측정과 책임 경계가 명확한 파일부터 한 기능씩 옮긴다. 로드/부팅 순서·명시적 dirty·성공 저장/실패 반환·서비스 bind와 epoch 검사를 유지한다. 전역 이름을 무작정 바꾸거나 함수 wrapper를 복원하지 않는다. TypeScript/프레임워크/빌드 도구 도입은 별도 비용·효과 판단 후 결정한다.

콘텐츠는 현재 담당자 한 명·매장/포장·대표 메뉴·지역 이야기 위에서 발전시킨다. 방문 고객의 공급/이탈까지 포함해 어떤 선택이 실제로 유용한지 측정하고, 초반 목표·일일 투자 결정·다음 지점 준비를 명확히 한다. 신규 지역/직원 수 확대는 현 6명·6지역의 반복 경험을 평가한 뒤 결정한다. 메뉴 해금의 가격 희석을 다시 숨기지 않으며, 미래 수익/비용/속도 변경은 동일 성장 모델로 전후를 비교한다.

연속 운영 모델 외에 하루 짧은 접속/수차례 접속/오프라인 위주의 모델을 추가해 수일 목표를 평가한다. 목표 달력 시간은 이 측정 뒤 정한다. 이미 확정한 미수령이나 과거 매출·기여도, paid 이력은 새 밸런스로 재계산하지 않는다.

## 서비스 쿠폰 범위

백엔드·계정·서버 인증 개발은 제외한다. 오프라인 기기 쿠폰과 직원의 제공 확인으로 운영한다. 음료의 테이블 방문당 1회는 여러 손님 기기 사이에 공유되지 않으므로 직원 확인과 함께 관리한다. 실제 혜택 발급/사용 운영 변경은 이 계획 작성에서 수행하지 않았다.

## 출시와 rollback 준비

누적 개선 브랜치 전체 diff를 검토하고 main의 구 자동 패치 워크플로·Pages legacy 설정을 다룬다. HTML/JS/SW 묶음과 대기 업데이트·구 문서·오프라인·기존 저장을 점검한 후보 SHA를 준비한다. 스테이징 origin의 검증이 운영 origin의 기존 저장 검증을 대신하지 않는다.

rollback은 현재 원 단위 encoding/저장 구조를 읽는 호환 버전으로만 연습한다. 문자열 금액을 읽지 못하는 오래된 main으로 되돌리거나 사이트 데이터를 지우는 것을 복구 절차로 삼지 않는다. 준비 결과를 리뷰한 뒤 main 병합·실제 배포는 별도 승인을 받는다.

## 모든 단계의 공통 완료 기준

- 직전 완료 SHA에서 새 작업 브랜치를 만들고, 한 단계에서 저장·정산·밸런스·출시를 한꺼번에 변경하지 않는다.
- 먼저 재현/측정 → 정책 → 최소 구현 → 실제 입력/실패·재시도 → 문서/보관 순서로 진행한다.
- 원 단위 금액, 확정 미수령/paid 미션·인증서·쿠폰, 직원 6명/본사·지점/운영·읽음, 서비스/연구 캐시, 엔딩 1회, 모달 입력, 작성자/인계, 명시적 dirty/저장, PWA 버전을 유지한다.
- 현재 197개와 단계마다 추가한 의미 있는 검사를 유지한다. `npm run doctor`, `npm run check`, `npm test` 및 최종 SHA의 CI를 확인한다. 미지원·미실행·skip을 통과로 기록하지 않는다.
- 단계별 커밋·측정/스크린샷·변경 방법/검증/남은 문제·다음 프롬프트를 남기고, 패치/번들/기준 SHA와 복구 tree 일치를 확인한다.
- 병합·배포·실혜택/운영 변경 승인은 해당 작업의 준비 결과를 리뷰할 수 있는 시점에 요청한다.

이번 계획 작성에서는 게임 코드나 저장을 변경하지 않았고 IMP-14 구현을 시작하지 않았다. 새 장애/성능/실기기 검증은 각각의 실행 단계에서 수행한다.
