# 성장과 원 단위 금액 정책

적용: IMP-10, 2026-10-12. 기존 [데이터 범위](data-ownership.md)와 [저장 계약](runtime-architecture.md)을 유지한다.

## 측정과 목표

`PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/ms-playwright" node scripts/measure-economy.cjs [비교할 트리]`는 실제 Chromium에서 설정·가격·처리량 함수를 사용한다. [변경 전](improvements/verification/IMP-10-economy-before.json)과 [변경 후](improvements/verification/IMP-10-economy-after.json)의 JSON을 보관한다. 시간 성능을 CI 임계값으로 쓰지 않는다.

기존 `2^53`원에 1원을 기록하면 매출은 1원 늘고 보유금은 그대로였다. 메뉴 연구 Lv.1200의 `100000 * 1.8^level`은 `Infinity`였고, 두 개의 매우 큰 유한 매출 합도 overflow될 수 있었다. 구 Lv.999 누적 매출은 약 `9.534×10^69`, 엔딩은 `9.99×10^70`원이다. 모든 연구·업그레이드·교육 최대, 메뉴 연구 Lv.10의 화성 체크포인트에서도 예상 분당 수익 약 `1.200×10^21`원으로 엔딩까지 약 `1.584×10^44`년이다. 이 설정은 일반적인 플레이로 엔딩에 도달할 수 없다.

사용자가 선택한 **수일간 누적 운영**을 목표로 확정했다. 지점 해금 비용·지점 가격/구매 배율·서비스 속도·연구 시간을 유지하고 엔딩 보유금 목표를 **100해 = 10^22원**으로 바꾼다. 엔딩은 누적 매출이 아니라 공용 보유금이며 한 번 해금한 플래그와 보상은 계속 유지한다.

| 연속 운영 모델의 시점 | 이전(분) | 이후(분) |
| --- | ---: | ---: |
| 부산 | 45 | 95 |
| 서울 | 131 | 208 |
| 일본 | 783 | 844 |
| 미국 | 1,855 | 1,722 |
| 화성 | 2,868 | 2,435 |
| 엔딩 | 30일 측정 범위 내 미도달 | 5,911 (약 98.5시간) |

모델은 분 단위의 연속 수익, 즉시 가능한 구매 중 수익 증가/비용이 큰 항목 우선, 직원 교육 10단계, 메뉴 연구 10단계, 실제 소요 시간을 쓰는 연구 슬롯 1개, 지점 이동 후 지역 연구 재시작, 하루 직원 임금 차감을 사용한다. 클릭·쿠폰 교환·이벤트·버프·엔딩 후 효과는 제외한다. 직원 교육은 공유하고 지점 성장/매출은 새로 시작한다. 가격·속도는 앱 함수로 계산하지만 **계획 모델의 평균 수익과 시간 적분은 Number 근사**다. 원 단위의 저장/정산 검증 자료와 구분한다.

자동 서빙을 `min(주문 유입, 자동 속도×2)`로 가정하고 배달 랜덤 간격은 40개 중점과 12% 휴식을 적분한다. 실제 고객 이동·인내심·이탈·화면 수용량은 모델에 없으므로 전체 소요 시간의 보장이 아니다. 구매 정책에는 선행 메뉴 해금의 장기 이익을 탐색하는 lookahead가 없다. 기존 후라이드 연구 후 다음 저레벨 메뉴를 열면 평균 주문 가격이 낮아져 메뉴를 계속 잠가 두는 전략이 나온다. 이를 숨기거나 최적 전략이라고 표현하지 않는다. 메뉴 수익 분포·구매 선택의 개선은 IMP-11의 선택 설계에서 다룬다.

별도로 완전 성장 화성에서 실제 `autoServe`, `updateDelivery`, `updateOnlineAuto`를 0.1초씩 10분 진행하고 seed 12345로 계측했다. 고정 체크포인트이며 고객은 유입률과 최대 10명에 맞춰 공급하고 인내심 손실/장면 이동은 제외한다. 측정 페이지에서만 저장 write를 생략하고 정산 함수는 그대로 사용한다. 실제 서비스 횟수와 매출은 JSON의 `actualTenMinutes`다. 이것을 처음부터의 실시간 장기 플레이로 주장하지 않는다.

오프라인은 기존 8시간 한도·자동 서빙 기본 속도·평판 계수만 사용하며 배달·온라인·팁 수입은 새로 추가하지 않는다. 장기간 미접속의 달력 시간은 위 연속 운영 모델보다 길다. 다음 밸런스 조정은 실제 플레이 기록을 보고 수행한다.

## 레벨 곡선

레벨 1은 0원, 2–10은 초반 수십만~650만원의 성장 구간이다. 이후 아래 앵커 사이를 기하 비율로 보간한다. 비율 계산은 계획용 실수 연산이고 임계 금액은 정확한 정수 연산으로 생성한다. 앵커는 직접 지정하여 실수 보간 오차가 끝점에 남지 않는다.

| 레벨 | 지점 누적 온라인+오프라인 매출 |
| --- | ---: |
| 10 | 6,500,000원 |
| 100 | 50,000,000,000원 (부산 비용) |
| 250 | 20,000,000,000,000원 (서울 비용) |
| 400 | 10,000,000,000,000,000원 (일본 비용) |
| 550 | 500,000,000,000,000,000원 (미국 비용) |
| 700 | 20,000,000,000,000,000,000원 (화성 비용) |
| 999 | 10,000,000,000,000,000,000,000원 |

지점별 레벨은 해당 지점 매출로 올라간다. 해금 비용을 지출했다고 지점 매출에서 빼지 않는다. 기존에 달성한 높은 레벨은 낮추지 않는다. 돈을 늘려 레벨을 복구하거나 기록 없는 수익을 추가하지 않는다. 새 곡선에 따른 추가 레벨은 기존 `checkLevelUp()` 경로에서 결정된다.

## 표현·정산·표시

- 단위는 정수 **원**이다. 금액 필드의 안전 정수는 기존 Number로 유지하고, 절댓값이 `Number.MAX_SAFE_INTEGER`를 넘으면 부호가 가능한 10진 정수 문자열로 저장한다. 작은 금액으로 내려오면 다시 Number다. 상태/JSON에 BigInt를 직접 넣지 않는다.
- 덧셈·뺄셈·비교·나눗셈은 `money.js`의 BigInt 연산이다. 보유금, 온라인/오프라인 매출, 메뉴 earned, 직원 career earned, 지점 기여도, 미분류 매출, 주간 매출 기준과 확정 미수령이 같은 단위를 쓴다. 수량·평판·시간·서비스 진행은 기존 Number다.
- 메뉴 기본 가격×확장×메뉴 연구×레벨×지역 + 가격 보너스, 마지막 매출 효과의 순서를 유지한다. 차원 없는 효과는 소수점 12자리로 정규화하여 `0.06×10` 같은 이진 오차를 제거한다. 분자/분모를 곱한 뒤 최종 원 단위에서 한 번 내림한다. 팁·온라인·배달·오프라인은 기존 정산 단계마다 각각 내림한다. 효과를 새로 중복 합산하지 않는다.
- 지수 비용은 정수 비율 거듭제곱으로 계산한다. 지역 비용 배율까지 곱하고 한 번 내림한다. 과거 부동소수점 반올림 오차로 1원이 달랐던 **미래** 가격/비용은 이 정책으로 통일한다. 이미 확정한 미수령 수익/내역은 다시 계산하지 않는다.
- 구매 버튼의 dataset과 실제 비용은 같은 함수다. 정확한 원 표기는 title에 넣고, 보고서/보유금은 한글 단위의 소수 두 자리 내림 표기를 사용한다. `10^72`원 이상은 세 유효자리의 `3.82×10^312` 같은 표기로 작은 화면을 보호한다. 표시를 다시 파싱해 구매/정산하지 않는다. 백업은 모든 정수 자릿수를 보존한다. XP만 0~1의 제한된 비율로 변환한다. 현재 레벨 앵커에서 다음 앵커까지 진행률을 표시하고 최고 레벨은 100%다.
- 음수 보유금(급여로 생긴 기존 부채)은 보존하고 표시한다. 구매·교환 비교는 음수를 그대로 판단한다. 메뉴/매출/보상은 비음수다.

## 저장 호환과 경계

저장 키·백업 키·수동 export envelope version 1은 유지한다. `moneyEncoding: "won-integer-v1"`을 루트에 추가한다. 예전 앱은 문자열 금액을 읽지 못하므로 새 백업은 IMP-10 이후 앱에서 가져와야 한다. 이전 Number 백업은 계속 지원한다.

기존 큰 Number는 `BigInt(Math.floor(value))`로 **이미 저장된 이진 값의 정수**를 옮긴다. 화면에 보이던 짧은 과학 표기에서 원래 의도한 정수를 추측하지 않는다. 이미 사라진 1원이나 미기록 매출을 만들지 않는다. 소수 원은 기존 보상/정산의 내림 정책대로 정수화한다. 확정 보상의 정수 금액과 이미 지급한 미션·인증서·쿠폰/사용 로그·엔딩 플래그는 변경하지 않는다. 알려진 금액 필드만 순회하며 확장 필드와 지점의 고아 staffStats를 합치지 않는다.

유효 문자열은 지수/소수/앞자리 0 없는 부호 있는 정수다. 4,096자리까지 받아 JSON/BigInt의 무한 길이 입력을 제한한다. 유한 Number의 309자리와 이번 엔딩 23자리를 충분히 넘는 범위다. 잘못된 금액 필드는 기존 sanitize와 동일하게 기본값(매출 0)으로 복구하며 import의 루트 money가 잘못되면 가져오기를 거부한다. 상한을 넘는 새 수익 기록은 모든 ledger 변경 전에 거부한다. 미수령 수령 중 범위/저장 실패는 기존 금액과 확정 receipt를 복구해 재시도할 수 있다. 상한을 넘는 입력을 무한/0으로 계산하거나 무한 돈을 지급하지 않는다.

메뉴 연구 구매는 10,000단계까지 허용한다. 그 비용은 약 2,558자리여서 유효 저장 범위 안이다. 과거 더 높은 연구 레벨은 지우지 않으며 추가 구매만 막는다. 연구의 가격 증가가 선형이고 비용은 지수여서 현실적인 진행 범위보다 훨씬 높다. Lv.1200의 overflow를 재현한 뒤에도 정확한 유한 비용·구매·재접속을 검증했다.

지점 snapshot·서비스 캐시·명시적 dirty/force save·실패 rollback은 기존 소유 코드가 관리한다. 금액 도우미는 저장 감시나 전역 함수 교체 래퍼를 설치하지 않는다. 새 사업 코드에서는 금액에 `+`, `-`, Number 변환, 문자열끼리의 `<`를 사용하지 말고 이 모듈의 API를 호출한다.

## IMP-16 선택 가능한 성장 목표

[모드 정책](campaign-policy.md)의 미래 지점 비용/지역 매출/가족 보유금만 선택한다. 가격·채널 수익·일반 구매·속도는 그대로이며 비용/경계는 기존 정확 원 API다. 구 저장은 legacy100해로 시작하고 선택 commit 실패는 원 상태를 유지한다. 확정 receipt를 다시 가격 계산하지 않고 과거 매출을 추가하지 않는다. 9채널 모델은 근사 시간 계획이며 실제 원 경계와 별도다. 기존5,000만원 교환/paid/사용 기록은 보존한다.
